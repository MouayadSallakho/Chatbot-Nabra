# Phase 39.6a: customers, team, roles, invitations and the member's own display name (Calm Glass)

Step 39.6a of the approved plan (`PHASE_39_0_REDESIGN_PLAN_REPORT.md`, sections 3.4, 3.6 and 12). Billing, plan and usage, workspace settings and notifications are 39.6b and were not touched.

## 1. Summary

- Customers, the customer page, the team, a member's page, the invite form and roles now use the Calm Glass panels and rows. Customers and members lead with the same avatars as the inbox, and every state is a chip with a word and a marker.
- An unnamed WhatsApp customer reads its masked number (`••••1234`) on the customer screens, as it does in the inbox. Each merge candidate now shows one code instead of two.
- Colleagues appear by the display name they chose, with the email address beside it. A past invitation names its sender the same way.
- Members set their own display name in a small dialog: "Change display name" is the first item in the account menu. The 80-character limit and the hidden-character rule are explained before anything is sent.
- The Arabic member block now reads «الأصوات تعمل» / «الأصوات متوقفة».

### 3.1 What changed and why

- **Customers (plan 3.6, notes 15 and 18).**
  - `CustomerRow` and `Customer` gain `reference` (39.1). `asLabelled` passes it through, so the inbox's label helper reads "WhatsApp customer ••••4821". An older read without it falls back to the short code.
  - The directory is a `.page-calm` panel of rows led by `app-avatar`: initials for a name, or the label code's first two characters ("7K", "48"), with the badge of the first channel. The skeleton draws this shape: the head, then a disc, the label, a channel and two end-aligned cells.
  - The customer page opens with a summary panel: the 64 px avatar beside four fact tiles. "How they reach you" and the history are radius-16 tiles. Rename and combine sit in the side column, unchanged in behaviour (`If-Match`, the stale notice, the unsaved guard, focus moves).
  - **One code per merge candidate (note 15).** The candidate line and the confirmation show the record's short code once: inside the label for an unnamed visitor, and after the facts otherwise (named, or WhatsApp labelled by its masked number). "ref." (the end of the record's id) is gone. In the merge sentence the code is isolated left to right with U+2066/U+2069.
  - `codeInitials` moved from the inbox list to `shared/avatar`. The customers chunk imports it from there, so it no longer pulls in the inbox list; the list re-exports it for its own callers.
- **Team, member, invitations (note 7).**
  - `MemberSummary.displayName` and `Invitation.invitedByDisplayName` (39.1), optional for an older server.
  - Team rows: a gold 40 px member avatar, then the display name (`<bdi dir="auto">`) above the email address (`dir="ltr"`). Owner and You are small chips. Without a display name the address is the title, shown once. Letters come from the new `shared/avatar/member-initials.ts`, which the account menu now uses too, so a member has the same letters everywhere.
  - Invitation states are chips: Waiting "i", Accepted tick, Expired hollow ring, Revoked plain. "Not checked" is a chip too.
  - A past invitation adds a second line under its date: "by Sara Ahmed (sara@…)", or the address alone. Past lists drop the empty Revoke column to give that line room.
  - Member page: the heading is the display name (or the address). A summary panel holds the 64 px gold avatar, the address when a name heads the page (with a hidden "Email address:" label), and three fact tiles. Owner, You and Protected are chips. The skeleton matches.
  - Invite page: calm panels, "Invitation created" is a success chip, and the link box is a soft tile. The language select, `#invite-email` and `role-option-{id}` are unchanged.
- **Roles.** Rows lead with a 36 px soft tile holding the roles glyph, with Protected (neutral) and Custom (hollow ring) chips. In the editor and the create page each permission area is a frameless soft tile with its name in title-3 and "n of m granted". Each permission keeps the family's checkbox, the whole row its 44 px target (`label.perm-option.choice-check`). The impact summary is a soft tile of small pills, and the skeleton draws the area tiles. `If-Match`, the stale notices and the guards are unchanged.
- **The member's own display name (plan 3.6).**
  - `AuthApi.saveDisplayName` sends `PUT /api/me/display-name` with `{ displayName }`; the XSRF header comes from the interceptor, as on every write.
  - `AuthService.saveDisplayName` updates the signed-in account on 204 with the normalised value, without a second session read. The session is still read only on load and focus.
  - `layout/profile-menu/display-name-dialog.ts` is a native `<dialog>` in the confirm dialog's glass, loaded with `@defer` the first time "Change display name" is chosen.
  - The dialog checks the rules in the server's own order: trim and collapse spaces, then 80 UTF-16 units, then control or format characters except ZWJ and ZWNJ. It uses the server's words (`display-name-problems.ts`) and registers them by code, so a server refusal reads the same way. An unknown code keeps the generic wording; the English `detail` is never shown.
  - Typed text survives a refusal. Save is guarded against double submission (`aria-disabled` while it runs). Saving an unchanged name closes the dialog without a request. Escape, Cancel and the scrim close it, and focus returns to the account menu's button.
- **Sounds pair (owner's note).** `account.soundsOn` / `account.soundsOff` in Arabic: «الأصوات تعمل» / «الأصوات متوقفة».
- **Styles.** `_admin.scss` gains a `.page-calm` block (fact tiles, area tiles, impact pills, the read-only role list as tiles, forced-colours edges) and the editor skeleton. Component styles changed only where the screen needed it, and every value comes from a token.
- **MASTER.md.** Seven decision-log rows, §13.5 (this step's contrast pairs) and §14.5 (the components).

## 4. Decisions

1. **The display name lives in a dialog, opened from the account menu (plan 3.6),** as its first item, because it is about the person, like the identity block above it. Loaded with `@defer`, it adds nothing to the startup JavaScript. Rejected: a profile page (a route, a page and navigation for one field).
2. **The dialog checks the two rules before sending,** in the server's order and words, and still words a server refusal by its code. Saving shows the new name at once from the normalised value instead of reading the session again: the rule allows session reads only on load and focus. Rejected: re-reading `/api/auth/session` after the save.
3. **No unsaved-changes guard in the dialog.** It is a single field in a modal: Escape, Cancel and the scrim discard on purpose, and the saved name returns when it reopens. The rule's guards (customer rename, member roles, role editor) are unchanged and checked live.
4. **One code per merge candidate (note 15):** the short code, never two. It is drawn from the same random end of the id as "ref." was, with 30 bits instead of 24, so it tells records apart at least as well. The masked WhatsApp number is a number, not a code: a WhatsApp candidate shows the number in its label and its short code once after the facts, because two numbers can share their last four digits.
5. **Display name and address together.** The team list and the member page show the name with the address under it; without a name, the address alone, once. Dialogs, toasts and the revoke and remove-all questions keep naming the email address (unchanged), because that is what identifies an account without doubt.
6. **Chip tones:** invitations Waiting "i", Accepted tick, Expired hollow ring (`draft`), Revoked plain. Roles: Protected neutral, Custom hollow ring. You: hollow ring. Each chip has a word and a marker (Q4). Using the `draft` ring for Custom and You marks "not one of the system's own", not "not in service"; the word carries the meaning.
7. **Inviter on its own line in past lists,** and the empty Revoke column dropped there. A name and an address in an 11rem column wrapped into three lines.
8. **Customer avatars** reuse the inbox's (`app-avatar`, first channel's badge) instead of the old first-letter tile, so the inbox and the customer screens agree (calm-glass §6 "Rows (inbox, customers)").
9. **Not shipped (honest gaps):** the invitation lists cannot say which language an invitation was sent in, because the invitation reads carry no `language` (backend ask BA39-6a-1). No WhatsApp customer exists in the dev data, so the masked number is covered by specs and the live contract (the field is present, and null for web visitors), not by a live screenshot.
10. **Departures from the specification or the boards:** none. No board covers these screens; they follow calm-glass §5–§6 and the plan. The 21st.dev MCP was not connected (authentication error), so the screens were built from our own primitives.
